# OOXML Explorer: Agent Development Guide & Instructions

Welcome, Agent! You are working on the **OOXML Explorer** repository — a React and TypeScript
web application that inspects, edits, compares and **analyses** Office Open XML documents
(`.docx`, `.xlsx`, `.pptx`) in the browser, using JSZip, Monaco Editor, and either Gemini or
an on-device model.

**The thing that makes this repository unusual is its analysis engine**, not its UI: 22
analyzers that detect faults which *render correctly and are broken anyway*. Read §2F before
touching anything in `services/` that produces findings.

This file is your development manual. Every rule below exists because breaking it produced a
specific, real defect here — several are written as warnings against instructions this very
file used to give.

**Before any substantial change, read
[`docs/ooxml-expert-agent/RESEARCH-STATE.md`](../docs/ooxml-expert-agent/RESEARCH-STATE.md)** —
the standing rules near the top, and the honesty ledger (§8) which records what is contested,
unverified, or has been retracted. Five citations have already been retracted on this project.

## 2. Core Architecture Rules

### A. State Management (Zustand)
- All shared UI, Editor, and Diff states MUST be managed through the unified Zustand store in [store/appStore.ts](../store/appStore.ts).
- Do NOT create local state for properties that require cross-panel or cross-view synchronization (e.g., active file path, pending changes, or sidebar toggles).
- **Tab State**: When modifying active tabs or files, update `editor.openTabs` and `editor.activePath` in tandem.
- **Resets**: When switching modes back to `'landing'`, always invoke the store's reset logic to purge stale file descriptors and prevent memory leaks.

### B. Zip & Pack Operations (Strict OOXML Compliance)
- All ZIP modifications MUST go through [services/zipService.ts](../services/zipService.ts).
- **Strict Pack Order**: When generating an exported OOXML package, the `mimetype` file **MUST** be placed first in the archive and **MUST NOT** be compressed (`STORE` mode in JSZip). Subsequent XML assets MUST be compressed using `DEFLATE`. Failing this order or compressing the mimetype will result in Microsoft Office rejecting the generated document as corrupted.
- Preserve compression modes of unmodified files when repacking.

### C. AI Integration — provider selection and prompt budgeting
- All AI queries, explainers, and structural audits MUST route through
  [services/geminiService.ts](../services/geminiService.ts) or
  [services/aiService.ts](../services/aiService.ts).
- **Never choose the provider yourself.** Call `getActiveAIProvider()` in
  [services/aiProvider.ts](../services/aiProvider.ts). **DLP mode is on by default**, which
  forbids cloud calls entirely: when local AI is unavailable the request must fail with
  `DLP_BLOCK` rather than quietly falling back to Gemini. A call site that picks its own
  provider is a privacy defect, not a style issue.
- ⚠️ **Do NOT slice file strings to a fixed character count.** An earlier version of this
  file told you to cap each file at 8,000 characters. **That instruction was the bug.** It
  applied per file with no total cap, above the provider branch, so a two-file diff sent
  ~10,700 tokens into a local window of 6k–9k that is *shared with the output* — and DLP
  users, who are forced local, were hit hardest. Use
  [services/promptBudget.ts](../services/promptBudget.ts), which computes a total budget
  from the session's reported `contextWindow` and divides it across the files.
- API keys are read via `getApiKey()`; a missing key throws `API_KEY_MISSING` so the UI can
  prompt for one. This applies to the **cloud** path only — under DLP mode no key is needed
  or wanted, and demanding one there was itself a bug once.

### D. Monaco Editor Themes & Word Wrap
- Monaco Editor configurations MUST use the theme definitions declared in [utils/theme.ts](../utils/theme.ts).
- Word wrap (`wordWrap: 'on'`) MUST be enabled for all editor and diff editor models to guarantee readable viewports.

### E. AI Request/Response Validation (Zod)
- Every exported AI service function's request and response shape MUST be a Zod schema (`z.object(...)`), with the TypeScript type derived via `z.infer<typeof Schema>` - never a hand-written `interface` for these shapes. See `EditorFileContextSchema`/`AIAnalysisSchema` in [services/geminiService.ts](../services/geminiService.ts) and `ElementExplanationSchema` in [services/aiService.ts](../services/aiService.ts) as the canonical examples.
- **Validate the request** at the top of the function (`Schema.parse(...)` or `.safeParse(...)`) before doing any work. This catches malformed callers at runtime, not just at compile time.
- **Validate the response** before returning it to the caller. This matters most for the on-device local model, which is not a constrained-decoding API and can return literally anything - Zod validation is what turns "the model returned garbage" into a caught, readable error instead of a silent type mismatch or a crash deeper in the UI. See `promptLocalModelForJson` in `services/geminiService.ts`.
- On a validation failure, throw a short, readable `Error` message - never let a raw `ZodError` (its `.message` is a JSON dump of every issue) reach the UI. Catch the parse call and rethrow with a message the AI panel can display directly.
- Scope: this rule covers the AI service layer's exported request/response contracts - the actual model I/O boundary in `services/aiService.ts` and `services/geminiService.ts` - not every internal helper type in the codebase.


### F. The Analysis Engine — the rules that matter most

Everything that reports a fault about a document goes through one type and one registry.

- **Every analyzer emits `Finding`** from [services/findings.ts](../services/findings.ts) —
  code, severity, part, message, remediation, `silent`. **Never author prose as a finding**;
  prose is *rendered from* findings at the boundary. That is what keeps the output consumable
  by CI or another agent.
- **Finding codes are a published contract**, namespaced `analyzer/kind`. Renaming one breaks
  callers and suppressions.
- **Register in [services/analyzers.ts](../services/analyzers.ts)**, and declare both
  `determines` and `cannotDetermine`. The second is not decoration — it feeds the capability
  ledger, which is how a clean run says *"no problems found by the checks that ran"* rather
  than *"this file is correct"*.

#### ⚠️ `silent` is the most dangerous field in the codebase

`silent: true` means *"renders correctly and is broken anyway"* — a claim the reader **cannot
check by looking**. Asserted about a healthy file it is the worst thing this engine can say,
and it has happened: a clean deck once reported that 12 things rendered correctly and were
broken anyway, when nothing was broken at all.

Before setting it, ask whether the fault is genuinely invisible. If it is already on the
page, it is `silent: false`. If it is not a fault at all — if it fires on the normal case, or
its remediation would begin *"no action needed"* — **it is not a finding**; put it in the
`explain` path instead.

#### The criterion for a new analyzer

§8u of the design record. A feature deserves an analyzer when it **fails invisibly**, which
three signals predict: indirection through `r:id`, paired markers matched by id, and
cached or duplicated state. Use the
[`add-analyzer`](skills/add-analyzer/SKILL.md) skill rather than improvising.

#### Two bug shapes this engine has produced twice each

- **First-match over a list of parts.** `matching(parts, WORD_BODY)[0]` read whichever body
  part the archive listed first — `word/footnotes.xml` in a real document — so comments
  anchored in the body looked orphaned *and* real faults there were missed. Every
  hand-written fixture has one body part, so `[0]` was always right. **Handle every match.**
- **An unwired module.** `ooxmlDiff.ts` sat unreachable for 489 lines; `issueReport.ts` for
  163; four resolver functions were built, tested and never called. **A module nothing
  imports is not finished.** Check with a reachability sweep, not by intent.

#### The evidence badge is computed, never asserted

`selectEvidenceTier` in [services/aiService.ts](../services/aiService.ts) derives
`verified | grounded | unverified` from provenance, in code the model never touches. **Do not
let a model report its own confidence.** The current rule lets the computation govern, which
is only safe because both inputs are mechanically derived — if you add a source that *can be
wrong*, it must go back to a minimum across sources. The doc comment there says so.

## 3. Style Guide & Design Aesthetics

This project uses a highly customized dark-mode first design system built with custom **Tailwind CSS HSL color tokens** mapped in [utils/theme.ts](../utils/theme.ts).
- **Primary Accent**: Use `#4A89DC` (representing standard document editing blue) for primary buttons, active states, and highlights.
- **Custom Selection Colors**: In dark mode, use Indigo/Slate transitions (`text-[#A5B4FC]` / `bg-[#A5B4FC]/10`) to distinguish diff modifications and pending states.
- Do NOT inject hardcoded color classes (like `bg-red-500` or `text-blue-600`) unless they are part of a theme-aware class returned by `useThemeClasses()`.
- Maintain clean animations: use transition-all classes for smooth panel collapses and hover states.

## 4. Testing & Verification

Two runners execute the same test files: **Vitest** on the terminal, and a **custom browser
harness** that proves the code works in a real browser. In the browser shim, `vi.mock` is a
**no-op that only warns** — so a browser-registered test runs against the *real*
implementation, which is a feature and has caught real defects. Know which you are in.

### ⚠️ Use `pnpm` to install, never `npm`

CI installs with `--frozen-lockfile`. `npm install` does not update `pnpm-lock.yaml`, so the
pipeline fails with `ERR_PNPM_OUTDATED_LOCKFILE` — which is exactly how it failed once, after
an agent added a dependency with npm. Running scripts with either is harmless; **installing is
not.**

### Commands

```bash
npx tsc --noEmit      # type check — `pnpm run build` does NOT fail on type errors alone
pnpm run lint
pnpm run test         # Vitest
npx playwright test   # E2E
pnpm run build
```

Generated data, only when you change its generator:

```bash
pnpm run ingest:schema   # rebuild public/rag-data.json from the Open XML SDK
pnpm run spec:facts      # rebuild tests/spec-facts.json from ECMA-376's XSDs (~8 MB download)
```

### ⚠️ MUTATION-TEST EVERY MODULE YOU TOUCH

**A green suite on first run is not evidence.** This is the single highest-yield rule in the
repository: deliberately breaking a module several ways and re-running its tests has found a
real gap in **nearly every module here**, and the usual find is *a test passing for the wrong
reason* rather than missing coverage.

`skills/add-analyzer/mutate.py` is the harness. Concretely, for each fix or new check:

1. Break the implementation in a way a plausible mistake would.
2. Run the tests. **They must fail.** If they pass, the test is asserting nothing.
3. Restore, and repeat for each distinct mistake.

Two traps worth naming, because both happened:

- **A surviving mutation is sometimes unfalsifiable code, not a missing test.** A guard whose
  condition no input can make false should be *deleted*, not covered. Both such cases here
  were removed with the reasoning recorded.
- **Test at the layer the bug lived.** A regression test for the first-match bug **survived
  reverting the fix**, because it called the inner function directly with explicit arguments
  and proved nothing about the caller's *selection* logic, which is where the bug was.

### Real Office files

The only check that can catch a **false positive on genuine Office output** — every other test
uses XML written by whoever wrote the code reading it.

```bash
pnpm run test:real
```

Fixtures go in `tests/fixtures/` and **the binaries are gitignored**, so that directory is
safe for confidential documents. Follow the
[`check-real-files`](skills/check-real-files/SKILL.md) skill: the first such run produced 43
findings across three files and **none was a real fault**, so triage is most of the work.

⚠️ **CI has no fixtures, so this suite skips there.** A green pipeline does not mean the engine
has been checked against real documents. `tests/syntheticPackages.test.ts` covers the
*structural* half in CI — when a real file exposes a structural bug, add the shape there.

### Registering a new test

New logic needs tests in `tests/`. To run them in the browser harness too, import them in
[services/testService.ts](../services/testService.ts).

## 5. Verification Checklist for Agents

Before declaring any task complete:

1. `npx tsc --noEmit` — **`build` alone is not a type check.**
2. `pnpm run lint`
3. `pnpm run test`
4. `pnpm run build`
5. **Mutation-test anything you changed** (§4). A green first run is not evidence.
6. If you touched an analyzer, confirm nothing became unreachable — an unimported module is
   not finished.
7. Record *what you did not verify.* Saying "this is untested against real files" is worth
   more than a confident claim that turns out to be wrong. Five citations have been retracted
   on this project already.

## 7. Standing Rules (from the design record, not to be re-litigated)

- **Deterministic first.** TypeScript decides what is true; the model narrates a pre-verified
  evidence bundle. It never plans, routes, or adjudicates correctness.
- **The badge is computed, never asserted.** Vector databases, re-ranking, embeddings on the
  main path and fine-tuning were each ruled out with reasons recorded in §5. Re-propose only
  with a new argument.
- **"Self-improving" means a gap log and a regression ratchet** — not a model writing its own
  rules or grading its own output. The loop closes through a person.
- **Mutation-test every module.**
- **Say what was not verified.**
